# Electron packaging — LeafMachine3 desktop shell

Phase 7 of the unified-runtime work: give `app/` a real packaging configuration for Linux,
Windows and macOS, build and smoke-test the Linux artifact, and be exact about which of the
other two were merely *configured* rather than *built*.

**Packaging does not block Linux Step 3.** Per the consensus plan (§1, "Deferred native
testing"), Windows and macOS qualification is a later release gate, not a prerequisite for the
Linux path. Nothing in this document gates Step 3, and nothing here should be cited as evidence
that the Windows or macOS builds work.

**Windows and macOS are "configured, cross-built where possible, never natively validated" — never
"passed."** Everything below was run on Ubuntu 22.04.5 x86_64. No Windows machine and no Mac was
involved at any point. No artifact was signed. No artifact was notarized.

---

## 1. Tool and versions

| | |
|---|---|
| Packager | **electron-builder 26.15.3** — pinned exactly (`--save-exact`), no range operator |
| Electron | **43.4.1** — unchanged, still pinned exactly (see `ELECTRON_UPGRADE.md`) |
| Node / npm | v24.18.1 / 11.16.0 |
| Host | Ubuntu 22.04.5, x86_64, kernel 6.8.0-111-generic, glibc 2.35 |
| Date exercised | 2026-08-29 |

`electron-builder` was chosen over `electron-forge` and bare `@electron/packager` because it is the
only one of the three that produces installers for all three platforms from a single declarative
config, it ships its own NSIS and `fpm` toolchains rather than requiring them from the host, and its
configuration is schema-validated (which is what makes the Windows/macOS stanzas checkable from
Linux at all — see §5). Forge would have meant adding a maker plugin per target and a JS config
module; `@electron/packager` produces app directories but no installers.

`npm install` also reported one install script it did not run:

```
npm warn allow-scripts   electron-winstaller@5.4.0 (install: node ./script/select-7z-arch.js)
```

`electron-winstaller` is the **Squirrel.Windows** maker. This configuration does not use it (the
Windows targets are `nsis` and `portable`), so the unrun script is inert. Do not "fix" it by
allowing the script; remove the concern by not adding a `squirrel` target.

## 2. Config layout

```
app/
  package.json               # electron + electron-builder pins, build scripts, homepage, desktopName
  package-lock.json          # regenerated by npm; never hand-edited
  electron-builder.yml       # the whole packaging configuration
  build/                     # buildResources -- TRACKED input, not output
    icon.png                 # 1024x1024 RGBA master; .ico and .icns are generated from it
    make-icon.py             # regenerates icon.png deterministically
    entitlements.mac.plist          # hardened-runtime entitlements for the main bundle
    entitlements.mac.inherit.plist  # ...and for the nested helper apps
  dist/                      # build OUTPUT -- gitignored, never committed
```

`.gitignore` needed two edits, both recorded there in comments:

- `/app/dist/` and `/app/.cache/` added, because a single Linux run leaves 645 MB in `app/dist/`.
- `!/app/build/` added, because the repo's pre-existing **Python** rule `build/` is unanchored and
  matches any directory named `build` at any depth — it was silently swallowing `app/build/`, which
  is tracked packaging *input*. The negation must stay after that rule to take effect. Verified with
  `git check-ignore -v`.

### What goes in the bundle

`files:` is an explicit allowlist — `main.js`, `preload.js`, `package.json`. There are zero
production dependencies (both Electron and electron-builder are `devDependencies`), so
`node_modules/` is not copied. The resulting `app.asar` is 18,990 bytes and contains exactly:

```
/main.js  /package.json  /preload.js
```

`main.js` and `preload.js` inside the asar are byte-identical to the sources (md5
`0a38b140126d1bad1cb4d3d811275ed8` and `99552ad3b05a99eb5f8ac4b0ddd45d5c`).

### Packaged layout — read this before shipping to a user

`main.js` computes the LM3 checkout as `ROOT = path.resolve(__dirname, "..")` and the interpreter as
`ROOT/.venv_LM3/bin/python`. In a packaged app `__dirname` is `<install>/resources/app.asar`, so
**ROOT becomes `<install>/resources`**. This was measured, not assumed — the packaged AppImage was
launched with `LM3_PYTHON` pointed at a stand-in script that prints its working directory:

```
[lm3] CWD=/tmp/.mount_LeafMakrPx0e/resources
ARGV=-m uvicorn leafmachine3.server.app:create_app --factory --host 127.0.0.1 --port 8801
```

Consequences, all of which are behavior of `main.js` (not of this packaging config, and not changed
here — `main.js` is owned by other steps):

- A packaged app **can attach** to an LM3 server that is already listening. This was smoke-tested
  end to end and works (§4).
- A packaged app **cannot spawn** an LM3 server with default settings, because
  `<install>/resources/.venv_LM3/bin/python` does not exist. `LM3_PYTHON` must be set to a real
  interpreter, or `main.js` must learn a separate "where is the LM3 checkout" setting.
- When `ensureServer()` fails, `main.js` calls `dialog.showErrorBox()`, which is **modal and
  blocking**. On a headless host the process then never exits on its own; the probe above had to be
  killed (`exit=137`). Not a packaging bug, but it makes automated packaged-app failure testing
  awkward.

Shipping a self-contained desktop app therefore needs a decision that is out of scope here: either
bundle a Python runtime as `extraResources`, or ship the shell as a thin client that is pointed at
an installed LM3.

## 3. How to build each target

All builds must scrub `ELECTRON_RUN_AS_NODE` and `ELECTRON_NO_ATTACH_CONSOLE` from the environment
first — see §6. Every command below was run under
`env -u ELECTRON_RUN_AS_NODE -u ELECTRON_NO_ATTACH_CONSOLE`.

| Script | Command | Notes |
|---|---|---|
| `npm run pack` | `electron-builder --dir --publish never` | dir-only, current platform, **3.5 s**. Use this for iteration. |
| `npm run dist:linux` | `electron-builder --linux --publish never` | AppImage + tar.gz + deb, x64. ~2m17s. |
| `npm run dist:win` | `electron-builder --win --publish never` | nsis (x64, arm64) + portable (x64). **Run on Windows.** |
| `npm run dist:mac` | `electron-builder --mac --publish never` | dmg + zip (x64, arm64), signed and notarized. **Run on a Mac with credentials.** |
| `npm run dist:mac:unsigned` | `CSC_IDENTITY_AUTO_DISCOVERY=false electron-builder --mac -c.mac.hardenedRuntime=false -c.mac.notarize=false --publish never` | local dev build on a Mac without a Developer ID |
| `npm run dist:all` | `electron-builder --linux --win --mac --publish never` | only meaningful in a matrix CI |
| `npm run validate:config` | `electron-builder --linux --win --mac --dir --publish never` | the cross-platform config exercise described in §5 |

`--publish never` is on every script, and `publish: null` is in the config, so no build can
accidentally upload anything.

macOS notarization credentials come from the environment, never from a file:
`APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID`, or `APPLE_API_KEY` +
`APPLE_API_KEY_ID` + `APPLE_API_ISSUER`. `mac.notarize: true` means a signed build **fails loudly**
without them rather than silently shipping something Gatekeeper will block.

The build needs the network on a cold cache: electron-builder fetched the Electron zip, the
AppImage runtime (`appimage-12.0.1.7z`), `7zip-linux-x64.tar.gz` and `fpm-1.17.0-ruby-3.4.3` into
`~/.cache/electron` and `~/.cache/electron-builder`. The network was available; nothing here is
simulated. A rebuild with a warm cache is offline for these downloads.

Two real defects were found and fixed during this work, not papered over:

1. The first `dist:linux` run **failed** the deb target with
   `⨯ Please specify project homepage, see https://www.electron.build/configuration#metadata`.
   Fixed by adding `homepage` to `package.json` (taken from `pyproject.toml`'s
   `Homepage = https://github.com/Gene-Weaver/LeafMachine3`).
2. It warned `desktopName is not set in package.json` — without it the running window's `WM_CLASS`
   does not match the installed `.desktop` entry, so GNOME/KDE show a generic dock icon. Fixed with
   `desktopName: leafmachine3.desktop` plus `linux.syncDesktopName: true`.

A `linux.desktop.entry` block with `Name`/`Comment`/`Categories` was also tried and **removed**: it
is dead configuration. Those three keys are owned by `productName`, `description` and
`linux.category`, and the values written into the `.desktop` file did not change. A separate build
confirmed that `desktop.entry` *does* apply to keys electron-builder does not own — `Keywords`
appears in the generated file — so the block was kept with only `Keywords` in it.

### 4.3 Linux smoke test — the shipped AppImage, launched and shut down

Run against a 60-line stand-in server that speaks the three endpoints `main.js` uses
(`GET /healthz`, `GET /`, `POST /v1/shutdown`), so the test exercises the packaged shell without
importing torch. `Xvfb :77` provided the display; the AppImage was executed **directly** (FUSE
mount, not extracted).

```
$ setsid node fake-lm3-server.js &                     # 127.0.0.1:8799
$ env -u ELECTRON_RUN_AS_NODE -u ELECTRON_NO_ATTACH_CONSOLE setsid \
    dist/LeafMachine3-3.0.0-x86_64.AppImage --no-sandbox --disable-gpu &

electron main pid = 2390186
child renderers: 9
--- app.log ---
[lm3-desktop] server attached at http://127.0.0.1:8799

$ kill -TERM 2390186

--- app.log after SIGTERM ---
[lm3-desktop] server attached at http://127.0.0.1:8799
[lm3-desktop] server stopped
--- fake.log ---
[fake] listening on 127.0.0.1:8799 pid=2390161
[fake] GET /healthz
[fake] GET /?token=370f53692f767516a97702ccd6c7513f
[fake] GET /healthz
[fake] POST /v1/shutdown
[fake] shutdown requested -- exiting
[fake] GET /healthz
--- survivors ---
(none - no orphans)
port 8799: no listener
```

So the packaged AppImage: launches, detects and **attaches** to an existing server, loads the UI URL
with its token, spawns its 9 helper processes, and on SIGTERM performs the full orderly teardown
(`POST /v1/shutdown`, confirm the port is quiet) leaving no orphaned process and no held port.

Two honest caveats on that result:

- **`--no-sandbox --disable-gpu` under Xvfb with SwiftShader.** Real GPU compositing and a real
  desktop environment are untested, exactly as in `ELECTRON_UPGRADE.md`.
- **The teardown shown above is behavior Step 5b is going to delete.** Today an *attached* server is
  killed on quit; the plan's Step 5b exit gate requires the opposite ("closing an Electron window
  attached to `lm3 serve` leaves that server and any run alive"). The smoke test proves the packaged
  binary faithfully reproduces *current* `main.js` behavior — it is not an endorsement of that
  behavior.

An earlier attempt at this test was **contaminated and discarded**: `pgrep` matched the `xvfb-run`
wrapper rather than the Electron main process, so the SIGTERM went to the wrapper. It is recorded
here only so nobody re-derives the same mistake. The run above targets the Electron main pid
directly.

## 5. What was validated for Windows and macOS — and what that proves

Three independent checks, in increasing strength.

### 5.1 JSON-schema validation against electron-builder's own schema

`app/electron-builder.yml` was validated against `node_modules/app-builder-lib/scheme.json` — the
same schema electron-builder applies at the start of every build — using the bundled `ajv`:

```
VALID: true
  recognized stanza: win  mac  linux  nsis  portable  dmg  deb  appImage
```

That is only meaningful because the schema is strict. **Negative control:** renaming
`mac.hardenedRuntime` → `hardenedRuntimeX` and `nsis.oneClick` → `oneClik` produces

```
NEGATIVE CONTROL VALID: false
  /mac must NOT have additional properties {"additionalProperty":"hardenedRuntimeX"}
  /nsis must NOT have additional properties {"additionalProperty":"oneClik"}
```

**Proves:** every key in the `win`, `mac`, `nsis`, `portable` and `dmg` stanzas is a real
electron-builder option, spelled correctly, with a type-correct value.
**Does not prove:** that any of those options produces the behavior intended, or that the values are
appropriate.

### 5.2 Cross-platform `--dir` build on Linux

`npm run validate:config` (`electron-builder --linux --win --mac --dir`) completed in 19.8 s and
produced app trees for all three platforms:

```
  • packaging       platform=darwin arch=x64 electron=43.4.1 appOutDir=dist/mac
  • skipped macOS application code signing  reason=supported only on macOS
  • packaging       platform=linux  arch=x64 electron=43.4.1 appOutDir=dist/linux-unpacked
  • packaging       platform=win32  arch=x64 electron=43.4.1 appOutDir=dist/win-unpacked
  • updating asar integrity executable resource  executablePath=dist/win-unpacked/LeafMachine3.exe
```

The generated **macOS** `LeafMachine3.app/Contents/Info.plist` reads back:

```
CFBundleIdentifier          = 'org.leafmachine.lm3'
CFBundleName                = 'LeafMachine3'
CFBundleShortVersionString  = '3.0.0'
CFBundleIconFile            = 'icon.icns'
LSApplicationCategoryType   = 'public.app-category.education'
NSHighResolutionCapable     = True
NSLocalNetworkUsageDescription = 'LeafMachine3 connects to its own analysis server running on this computer.'
LSMinimumSystemVersion      = '12.0'
ElectronAsarIntegrity       = {'Resources/app.asar': {'algorithm': 'SHA256', 'hash': '8746584f…'}}
```

with the four helper bundles present (`LeafMachine3 Helper`, ` (Renderer)`, ` (GPU)`, ` (Plugin)`)
and `icon.icns` generated from `build/icon.png`. The **Windows** tree produced `LeafMachine3.exe`
carrying a rewritten version resource (`ProductName` = `LeafMachine3`) and `icon.ico` (7 sizes,
16×16 through 1024×1024) generated from the same PNG.

**Proves:** the config is *consumable* for all three platforms; the appId, product name, category,
`extendInfo` keys and icons land where they should; the asar allowlist applies identically on all
three; the icon master converts cleanly to `.icns` and `.ico`.
**Does not prove:** anything about execution. The macOS `.app` was built on Linux, is unsigned, and
its Mach-O binaries have never been loaded by macOS. The `LeafMachine3.exe` has never been executed
by Windows.

```
  • downloaded      label=nsis-3.0.4.1.7z progress=100%
```

```
$ electron-builder --mac dmg zip --publish never

  • building        target=macOS zip arch=x64 file=dist/LeafMachine3-3.0.0-mac-x64.zip
  • building        target=DMG arch=x64 file=dist/LeafMachine3-3.0.0-x64.dmg
```

The `nsis` target got as far as fetching its whole toolchain and driving the NSIS stub before
needing `wine`, which is not installed here. It left a 233 KB `…-x64-setup.exe` — **that file is a
truncated intermediate, not a usable installer**, and it was deleted. Wine was deliberately *not*
installed: a wine-built installer still proves nothing about how Windows executes it, so the cost
would buy no evidence.

**Proves:** the target definitions are reached and driven by electron-builder — the failures are
missing *host toolchains* (`wine`, `sips`), not configuration errors.
**Does not prove:** that `nsis`, `portable` or `dmg` produce a working installer.

## 6. The `ELECTRON_RUN_AS_NODE` trap

`ELECTRON_UPGRADE.md` documents it; it still applies and it was re-measured today. This environment
exports `ELECTRON_RUN_AS_NODE=1` and `ELECTRON_NO_ATTACH_CONSOLE=1`:

```
$ env -u ELECTRON_RUN_AS_NODE -u ELECTRON_NO_ATTACH_CONSOLE ./node_modules/.bin/electron --version
v43.4.1
$ ./node_modules/.bin/electron --version          # the trap
v24.18.1
```

`v24.18.1` is the bundled **Node** version and exit status is 0, so an unscrubbed check looks like a
plausible green and means nothing. **Every** command in this document — every build, every version
check, every smoke test — was run under
`env -u ELECTRON_RUN_AS_NODE -u ELECTRON_NO_ATTACH_CONSOLE`. Any packaging CI job must do the same.

(The one deliberate exception: `ELECTRON_RUN_AS_NODE=1` was set *on purpose* in §4.2 to read
`process.versions` out of the packaged binaries without launching a window. `process.versions.electron`
is correct under that variable; only the `--version` **flag** is not.)

## 7. NOT VALIDATED ON THIS HOST

Everything in this list is unproven. None of it may be reported as passing.

**macOS — nothing was run.**
- [ ] No `.app` was launched. The `.app` in §5.2 was assembled by Linux and never loaded by macOS.
- [ ] **No code signing.** electron-builder said so itself: `skipped macOS application code signing
      — reason=supported only on macOS`. Requires a real Mac and a Developer ID Application
      certificate in a keychain.
- [ ] **No notarization.** Requires a real Mac, an Apple Developer account, and either an app-specific
      password or an App Store Connect API key. **Not attempted.**
- [ ] No stapling, no Gatekeeper / quarantine behavior, no `spctl --assess`.
- [ ] The hardened-runtime entitlements are **untested**. They parse as valid plists
      (`plistlib.load` on both), and every key is a documented Apple entitlement, but whether they
      are sufficient — in particular whether `disable-library-validation` +
      `allow-dyld-environment-variables` actually let the hardened app spawn an unsigned Python and
      load the LM3 virtualenv's dylibs — can only be established on a Mac.
- [ ] No `dmg` was produced (`sips` is macOS-only).
- [ ] arm64 (Apple silicon) was never built or run. Only the x64 `--dir` slice was assembled.
- [ ] `NSLocalNetworkUsageDescription` lands in `Info.plist`, but the macOS 13+ local-network
      permission prompt has never been seen.

**Windows — nothing was run.**
- [ ] No `.exe` was executed. `LeafMachine3.exe` was assembled by Linux and never loaded by Windows.
- [ ] **No NSIS installer was produced** — the target fails on missing `wine`.
- [ ] No `portable` build was produced.
- [ ] No code signing configuration exists at all, so installers will be unsigned and will raise a
      SmartScreen "unrecognized app" prompt.
- [ ] Install, upgrade-over-install, uninstall, shortcuts, `%LOCALAPPDATA%` handling: all untested.
- [ ] Windows process-tree behavior (job objects, killing a tree rather than orphaning children) is
      entirely untested; `main.js`'s shutdown path is POSIX process-group based
      (`process.kill(-pid, …)`), which has no Windows equivalent.
- [ ] arm64 was never built.

**Linux — the gaps that remain even though the build passed.**
- [ ] The `.deb` was never installed with `dpkg -i` / `apt install`; only unpacked and inspected.
- [ ] The `tar.gz` payload was never launched (only its Electron version and asar were read).
- [ ] No Wayland session — this host is X11-only.
- [ ] No real GPU: every launch used `--disable-gpu` under Xvfb (SwiftShader).
- [ ] `--no-sandbox` on every launch. The sandboxed path in a packaged AppImage is untested.
- [ ] The **real** LM3 server and the real LM3 UI were never loaded — the smoke test used a
      stand-in server, deliberately, so the Chromium 130 → 150 renderer jump remains untested
      against `leafmachine3/server/ui/` exactly as `ELECTRON_UPGRADE.md` says.
- [ ] x64 only; no arm64 Linux build.
- [ ] Auto-update is not configured (`publish: null`) and was not tested.

## 8. Where this sits in the plan

- Packaging is Step 5a's "smoke-test packaging" clause, finished here. **It does not block Step 3.**
- `requestSingleInstanceLock()` is still deliberately absent from `main.js` — Step 5b owns it. This
  change added no application code.
- Native Windows and macOS qualification is a **later release gate**. `NATIVE_ACCEPTANCE_CHECKLIST.md`
  is the checklist for that gate, and it marks which plan step must land before each item is even
  testable.
- Re-pin Electron before **2027-01-05** (43.x EOL) per `ELECTRON_UPGRADE.md`.
