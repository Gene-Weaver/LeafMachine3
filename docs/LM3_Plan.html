LeafMachine3 — a clean, resumable, GPU-saturating specimen pipeline

A symbolic architecture for the runtime LeafMachine3 package: a single YAML control surface, a per-project SQLite database, a tiny sequential manager (machine3.py) that mirrors LeafMachine2's machine.py, and modules that each saturate all available hardware. This is the reconciled blueprint a developer turns into the real repo.

Scope runtime / deployment repo (ships exported models only) Not the /datac/Labelbox_Dump training area Style PEP8 · typed · dataclasses · pathlib · one DAL Method designed & adversarially reviewed by an 11-agent workflow

LeafMachine3 (LM3) is the production successor to LeafMachine2. The /datac/Labelbox_Dump tree is the training area where each component is trained and exported; LM3 is a separate, new repository that ships only the trained ONNX/OpenVINO artifacts plus this orchestration code. LeafMachine2's machine.py is the structural reference — same spine — but LM2 is fractured and dead-code-laden, so LM3 pushes every concern (models, SQL, threading, resume) behind a small set of collaborators and keeps the manager readable.

◆ Two control surfaces + a one-time hardware profile

1 · LM3_settings.yaml — the settings surface: user intent (paths, model choices, quality knobs). Inputs.

2 · the project_status table (in the per-project SQLite DB) — the progress surface: skip / resume / staging. Outputs. Point the YAML at an output dir that already holds a project DB and LM3 resumes — skipping whole finished modules and, within a partial module, the images already done.

+ hardware_settings.yaml — written once by LM3_Setup (§7): the machine-tuned performance layer (workers, batch, queue sizes, tmp location, GPU/VRAM, precision). Cached so runs never re-probe; rerun it from the CLI or the GUI when the hardware changes.

1Architecture at a glance

2The manager — machine3.py

The manager is the anti-LM2: the exact eight-beat spine of LeafMachine2's machine(), but each beat delegates to one collaborator, so the function fits on a screen with zero commented-out code. It sets the spawn start method before any CUDA import, loads and validates the YAML, builds the output tree, starts logging, fails fast if an exported artifact is missing, opens-or-creates the project DB (an existing DB means resume), reclaims any stale running state from a prior crash, ingests images, then runs the ordered pipeline.

3The stage contract

Every module subclasses one PipelineStage. The contract is split cleanly across the process boundary, which is what makes the pipeline both correct under concurrency and trivially extensible:

  • collect_items(project) runs on the parent (which owns the DB): it reads inputs from prior stages and returns self-contained, picklable WorkItems.
  • build_model(device) and infer(item, model) run inside each worker: warm-load once, then pure compute. Workers never touch the database.
  • persist(project, item, payload) runs back on the parent collector, inside one transaction with the per-image checkpoint — a single writer, an atomic checkpoint.

Adding a stage is genuinely "implement three methods and add one line to STAGE_ORDER." The resumability methods have DB-backed defaults, so a typical stage never overrides them.

✓ Why this split is the correct one

An earlier draft had workers writing their own rows through a shared connection. That is unsafe — SQLite gives single-writer concurrency across connections, not concurrent use of one connection — and it makes the stage un-picklable (the connection can't cross a spawn). Confining all writes to the parent collector fixes both, and lets each stage still write its own tables via persist.

4Pipeline order & the run loop

STAGE_ORDER is the single source of truth for stage identity and sequence; every other layer imports STAGE_KEYS from here, so the four-way key drift that used to break the ledger's foreign key is impossible by construction. The run loop owns exactly three cross-cutting concerns — skip-if-done, config-drift detection, and the restart cascade — none of which leak into the manager or a stage.

Three subtle correctness rules are wired here: a stage is marked done only when its per-image ledger is genuinely drained (so newly-added or errored images re-open it); a done stage whose resolved settings or model artifact changed is forced back to pending (the DB always corresponds to the YAML that produced it); and --restart KEY invalidates that stage and its transitive dependents, cascading the cleanup so no downstream output is left computed from stale inputs.

6Control surface #1 — LM3_settings.yaml

One hand-editable file drives an entire run. It is organized into project (I/O + run/resume policy), compute (devices, VRAM-based worker sizing, onnxruntime providers), modules (one block per stage, each exposing the model artifact plus most of that model's runtime knobs), and report (the Reporter output switches). The organizing principle: the YAML holds inputs; high-cardinality per-crop outputs live in the DB method tables — the one deliberate exception being the final CF duplicated onto the specimen row.

7LM3_Setup — one-time hardware auto-tuning

The YAML holds what the operator wants; it should not also carry values that depend on the specific box it runs on. LM3_Setup is a separate module (python -m leafmachine3.setup) that profiles the machine once per install and writes hardware_settings.yaml — the machine-derived layer every module reads. It is rerunnable any time (CLI --force, or the GUI's Hardware Setup panel), and a normal run auto-detects when the profile has gone stale.

What it measures and writes

  • GPU inventory — count, model, total & free VRAM (NVML), driver; or "CPU-only" when none.
  • Bound execution provider — which EP actually engages under the GPU-first ladder (CUDA / DirectML / CoreML / OpenVINO / CPU) and the best precision (fp16 vs fp32, after a speed + parity check).
  • Tmp location — benchmarks write-speed and free space of candidate dirs and picks the fastest local disk with headroom (so _tmp working copies never land on a slow HDD or a network mount).
  • Per-stage throughput plan — the slow, once-only part: short dry runs sweep (batch, workers_per_gpu) on a sample of representative crops, keeping the combo with the highest images/sec that still fits VRAM with the safety margin. Queue size follows the pool. CPU stages get a worker count from the core count.
  • Fingerprint — OS/CPU/RAM, GPU set, driver, onnxruntime version, and a hash of each exported model, so a later run can tell the profile apart from the current machine.
◆ How the three files compose

Precedence for any performance value is built-in defaults < hardware_settings.yaml < LM3_settings.yaml (explicit, non-"auto") < CLI. So a knob left as "auto" resolves from the tuned profile (no re-probe), while an operator who hard-codes workers: 4 still wins. The executor takes a fast path — it reuses the cached optimum instead of live-probing VRAM every run — and only falls back to probing when no profile exists yet.

Running once, and rerunning

Missing file → auto-run once. If hardware_settings.yaml does not exist, machine3() runs the full LM3_Setup automatically (the dry-run optimization) before the pipeline starts, so the very first run is already tuned. This is the only time it runs itself, and it may take a few minutes — then it is cached for every future run.

File present → stays separate / on-demand. Once the profile exists it is never re-run automatically. It is used as-is; a normal run only logs a suggestion to re-tune if the fingerprint drifts (GPU set, driver, onnxruntime, or a model hash changed). You rerun it deliberately: python -m leafmachine3.setup --force, or the GUI's Re-run optimization button (which streams the dry-run sweep so you see progress on the multi-minute pass). The desktop installer can also fire it once post-install so a packaged app is tuned on day one.

8Control surface #2 — the project database

One SQLite database per project (WAL mode) in the output dir. A specimen metadata table holds one row per input image; a table per ML method records every box/instance with provenance back to its parent; and project_status + image_status form the two-level ledger that drives resume.

◆ Mask reconstruction — geometry, not pixels

Each leaf instance stores its polygon / COCO-RLE in parent (working) coordinates plus its bbox and a link to the source detection — never a rendered PNG. Every Reporter view is then a pure function of (original pixels, geometry), rebuilt on demand: binary mask, RGB-on-black, RGB-on-white, box+mask overlay, masked subset crop, or a derived dataset. Geometry is kilobytes (vs. many full-res PNGs per leaf), view-agnostic (the user picks views later in the YAML), and loss-free (color views resample the immutable original). Because ingest may downscale an oversized original, the specimen row also stores original_width/height and work_scale, and Reporter scales geometry by 1/work_scale before compositing onto the full-res original — so overlays never misregister.

The data-access layer

All raw SQL lives in one ProjectDB class. Its method surface is the contract every stage calls; the collector is the sole writer, and detection writes are delete-then-insert inside one transaction so a torn write or a restart can never duplicate boxes.

9The concurrency engine

This is what turns "sequential stages" into "sequential stages that each pin every GPU at 100%." Persistent worker processes (spawn — own CUDA context, own ORT session, GIL-free, crash-isolated) pull WorkItems from a bounded queue as they finish, so a slow 12k-pixel sheet never head-of-line-stalls the others and memory stays flat under backpressure. Worker count is sized by probing one warm worker's real VRAM footprint on a large image and dividing the free budget — not a static guess — with staggered warm-loads so peak VRAM ≈ steady state. The parent is the single writer, checkpointing each result atomically.

▲ The onnxruntime silent-CPU trap

GPU onnxruntime silently falls back to CPU (10× slower) if the venv's bundled CUDA libs aren't on LD_LIBRARY_PATH when the session is created. The loader reads that variable at process start, so LM3 sets it in the launch environment (spawn children inherit it) and re-execs once if it was missing — then asserts the CUDA EP actually bound unless allow_cpu_fallback is set.

10Image ingestion & the immutability contract

Originals are strictly read-only and never modified. If an image isn't exactly .jpg or exceeds the working-dimension cap, a converted copy (q≈100) is written to _tmp and symlinked into the working set; otherwise the original is symlinked unchanged. Downstream, every stage opens one path — working_path — and never branches on "modified vs. original." Ingestion is idempotent and resumable: a re-run skips originals whose size+mtime are unchanged and whose symlink still resolves.

11Resumability — how the surfaces cooperate

The YAML says what to do; project_status says how far we got. Together they make a run fully restartable at two grains:

  • Whole-module skip. is_complete is true only when a stage is done and its per-image ledger is drained. So a finished stage is skipped — but a batch of newly-ingested images (or images left in error) re-opens it automatically.
  • Within-module resume. The executor snapshots the done set before dispatch and processes only the remainder; each finished image is checkpointed atomically, so a kill -9 mid-stage resumes exactly where it stopped. A crashed worker is detected by a liveness timeout rather than hanging the run, and stale running state is reclaimed to pending at startup.
  • No-work seeding. A sheet with no ruler has no work for the ruler stages; the executor marks those image_status rows done (no_work=1) so a downstream depends_on gate never stalls waiting on a checkpoint that would never arrive.
  • Restart cascade. --restart ruler_cf purges that stage's rows, nulls the specimen columns it owns, deletes its tracked crop/report files, resets the ledgers, and recurses into its dependents — so grounded areas can't keep an old CF.
  • Config-drift guard. A per-stage settings_hash forces a rerun when the resolved settings or the model file changed, so the DB never silently disagrees with the YAML.

13Packaging & deployment — beating pip-install hell

The single biggest lever: LM3 runs exported ONNX/OpenVINO models at inference, so the heavy training stack shrinks dramatically. The runtime tree is a GPU-capable onnxruntime + numpy + opencv-headless + pillow + fastapi/uvicorn — small enough to bundle cleanly, which is what turns packaging from "impossible" (LM2's reputation) into a solved pattern.

✓ GPU is the default at runtime — CPU is only the fallback

Two questions get conflated. (1) Runtime: the pipeline defaults to devices: auto, which is GPU-first — it uses every visible NVIDIA GPU and drops to CPU only when no accelerator exists. The whole VRAM-saturation engine is GPU-centric, and a GPU that is present but whose EP fails to bind is a hard error, not a silent slow CPU run. So "everything is CPU by default" is never how you run it. (2) Distribution: the only real choice is which onnxruntime the installer ships — and the base install is GPU-capable, so an NVIDIA card is used automatically.

Provider selection is GPU-first and automatic: NVIDIA CUDA / TensorRT whenever available, then a non-CUDA GPU path (DirectML on any Windows DX12 GPU, CoreML on Apple Silicon, OpenVINO on Intel), and CPU only as the backstop when no GPU is found:

Server mode + the Electron sidecar

lm3 serve is a thin FastAPI shell over the same machine3() pipeline — one project DB per job, so it inherits resume for free. It runs one heavy job at a time and lets each stage's internal queue saturate the hardware, exactly as the CLI does; HTTP concurrency is only for status/SSE reads.

The desktop app is Electron (or Tauri) owning the UI and spawning that Python server as a bundled child process, talking to it over loopback HTTP + SSE. The renderer is just a web client; on a crash the main process restarts the sidecar and the job resumes from its SQLite DB.

◆ Recommended path — GPU-first, platform-aware base install

An Electron (or Tauri) desktop app bundling a Python sidecar built as a relocatable conda-forge environment via constructor + micromamba, GPU-capable by default. Runtime behavior is GPU-first with automatic CPU fallback everywhere; the base install ships a GPU runtime so an NVIDIA card is used out of the box:

  • Linux (your lab box) — bundle onnxruntime-gpu + CUDA + cuDNN via conda-forge, so every NVIDIA GPU runs on GPU by default. Heavier (~2–3 GB CUDA) but it is the only GPU path on Linux and exactly how you run the multi-GPU pipeline. An optional lean CPU-only build covers headless / no-GPU boxes.
  • Windows — bundle the DirectML EP: NVIDIA (and AMD/Intel) GPUs accelerate with zero CUDA install, small download. Optional CUDA/TensorRT max-throughput pack for NVIDIA power users who want the last bit of speed.
  • macOS — bundle CoreML (Apple GPU / Neural Engine); no NVIDIA or CUDA exists on modern Macs.

Why conda-forge / constructor: it resolves onnxruntime + CUDA + cuDNN + opencv as ordinary packages (no hand-assembled DLL sets → no silent-CPU trap) and emits signable per-OS installers that drop straight into the Electron resources/pyenv/. CPU is the automatic fallback, never the intended default. Docker ships too, for lab servers / IT.

Cross-platform + trust: Authenticode/EV signing on Windows to dodge SmartScreen; a Developer-ID signed and notarized build on macOS (a loose pip tree of unsigned .sos fails notarization — another reason to control the env via constructor); an AppImage plus the Docker image on Linux. Auto-update via electron-updater, with the base app and the optional CUDA/TensorRT pack on separate channels so a routine app update never drags CUDA behind it. The project DB records the pipeline + model version that produced it — reproducibility for a science audience.

14Roadmap — from this plan to a running repo

  1. Scaffold the package — leafmachine3/ with the layout above; port the four inference/ wrappers verbatim from the training repo.
  2. Core spine first — config.py, db.py + schema.sql, stage.py, executor.py, ingest.py. Get a one-stage pipeline (ArchivalDetector) running end-to-end with real checkpointing before adding stages.
  3. LM3_Setup — the machine profiler + hardware_settings.yaml; start with the quick heuristic profile, then add the dry-run sweep. Every later step reads its tuned worker/batch/tmp values instead of guessing.
  4. Fill in stages 2→8 one at a time; each is "implement three methods + one STAGE_ORDER line." Verify resume and --restart after each.
  5. Golden-run tests — a tiny fixture project asserting: kill-and-resume produces identical rows; a changed conf triggers a config-drift rerun; a 0-ruler and a 2-ruler sheet ground correctly.
  6. Server + desktop — lm3 serve, then the Electron sidecar and the constructor CPU bundle; add the GPU Pack channel last.

The payoff of running exported models instead of the training stack is one uniform pipeline, portable artifacts, and layered acceleration — a tool a biologist can actually install.
